# Soma Nami app

iOS and Android app from one codebase, built with Expo SDK 54 as a dev build (native projects generated by `expo prebuild`, not Expo Go) and the QVAC SDK for on-device AI. iOS (Wesley's iPhone 12) is the development and demo device; Android testers install an APK built in GitHub Actions.

## Versions

| Package | Version |
|---|---|
| `@qvac/sdk` | 0.22.0 (exact) |
| `react-native-bare-kit` | 0.16.0 |
| Expo SDK | 54 (React Native 0.81) |
| iOS | deployment target 17.0, arm64 with Metal, physical device only (QVAC) |
| Android | minSdk 29, arm64-v8a only; QVAC needs Android 12+ on arm64 and a physical device |
| Node.js | `^22.21.0 \|\| >=24.9.0` (needed by QVAC's mobile bundler) |

QVAC plugins bundled (`qvac.config.json`, JSON only in Expo): OCR (`ggml-ocr`), TTS (`tts-ggml`), speech recognition (`whispercpp-transcription`), LLM (`llamacpp-completion`). The audio decoder is off; C5 turns it on if recordings need decoding before Whisper.

## Where QVAC is called

- `src/model-store/qvacClient.ts`: `getModelInfo` (is a model on the phone?), `downloadAsset` (fetch it), `cancel`.
- `src/reader/qvacReader.ts`: `loadModel` / `unloadModel` for OCR (`OCR_LATIN` + `OCR_CRAFT`) and the English voice (`TTS_MULTILINGUAL_SUPERTONIC3_Q4_0`), `ocr` on the photo, `textToSpeech` for each label line.
- `scripts/phrases/generate.mjs` (on the VPS, not in the app): `textToSpeech` with Chatterbox multilingual to pre-render the fixed Swahili phrases.
- `app.json`: `@qvac/sdk/expo-plugin` bundles the QVAC worker and links its native addons at prebuild.

## Reading (card C4)

Home → camera (tap anywhere to take the photo, or **Chagua picha** to pick one) → QVAC OCR on the phone → the label lines in large type, read aloud. The code, in order:

| Step | File |
|---|---|
| Shrink the photo to 1280 px on the long side (a full 4032 × 3024 photo would blow OCR's memory) | `src/reader/services.ts`, `src/reader/image.ts` |
| OCR with `canvasSize 1024`, `recognizerBatchSize 1` (the C2 spike's low-memory settings, 1.7 GB peak on the VPS instead of 3.2 GB) | `src/reader/qvacReader.ts` |
| Blocks → visual lines; any line whose weakest block is below confidence 0.5 is marked unsure | `src/reader/ocrLines.ts` |
| What to do with the photo: read it; or a spoken hint (move left/right/up/down, further, closer, no text found) and try again, with **Soma hii** to read what was found anyway; or **Not sure** for a page that's mostly unreadable or looks like a handwritten dose ("1x3", "2 bd", "Tab 1 tds") | `src/reader/assess.ts` |
| What is said: each confident English line exactly as printed (Supertonic, on the phone); an unsure line is never read, the app says it couldn't read it and to ask the pharmacist; Swahili lines are shown, and a clip says once that they're on the screen (no Swahili voice runs on the phone) | `src/speech/plan.ts` |
| Speaking, highlighting the spoken line, prefetching the next line, stop and restart | `src/speech/session.ts`, `src/speech/expoAudioBackend.ts` |
| Screens | `src/screens/read/` |

Only one model is loaded at a time (`src/reader/exclusiveModels.ts`): OCR is unloaded before the voice loads and vice versa. Each read logs `[soma] ocr <ms> ...` to the Xcode console.

### Swahili phrases

Every fixed Swahili line the app speaks (prompts, hints, the not-sure lines, button read-backs) is in `assets/phrases/phrases.json` and ships as a pre-rendered clip in `assets/phrases/sw/<id>.m4a`. Chatterbox is too slow to run on the phone (C2: 30–47× slower than real time), so the clips are made on the VPS:

```bash
cd mobile
node scripts/phrases/generate.mjs            # renders new or changed phrases only (~2-4 min each on one core)
node scripts/phrases/generate.mjs --only hint_left,hint_right
node scripts/phrases/generate.mjs --force    # everything
```

It needs ffmpeg and `@qvac/sdk` 0.22.0 with desktop prebuilds (set `QVAC_SDK=/path/to/node_modules/@qvac/sdk` if the one in `mobile/` lacks them). It rewrites `src/speech/phraseAssets.ts` and `assets/phrases/phrases.lock.json`; `src/speech/phrases.test.ts` fails if a phrase has no clip. Clips are AAC, mono, 24 kHz, about 10 kB each.

## Theme

`src/theme/` holds the design tokens from `docs/ui.md`: dark theme by default (`#0E0E0E`, yellow `#FFD60A` main action, blue `#8EC9FF` ask, orange `#FF9F43` not sure, black text on every accent), a light theme for caregiver setup, type sizes (body ≥ 20, headings 30–52) and the 88 pt touch target. Screens read colours with `usePalette()` and never hard-code them. `src/theme/tokens.test.ts` checks every text/background pair reaches WCAG AAA (7:1).

Font: Atkinson Hyperlegible Regular and Bold (SIL Open Font License, `assets/fonts/OFL.txt`), embedded in the native app by the `expo-font` config plugin, so it is there with no network. Use `fonts.regular` / `fonts.bold` instead of `fontWeight`. A font change needs a new native build (`expo prebuild`).

## Models

Downloaded once, on Wi-Fi, from the models screen. The app won't open the reader until all of them are on the phone, so after that it works in airplane mode.

| Model (QVAC registry constant) | Used for | Size |
|---|---|---:|
| `OCR_CRAFT` | finding text in a photo | 83 MB |
| `OCR_LATIN` | reading Latin-script text | 15 MB |
| `TTS_MULTILINGUAL_SUPERTONIC3_Q4_0` | English voice | 85 MB |
| `WHISPER_SMALL_Q8_0` | hearing hold-to-talk questions (C5) | 264 MB |
| `QWEN3_1_7B_INST_Q4` | answering questions about the label | 1,057 MB |
| **Total** | | **≈1.5 GB** |

The list is `src/model-store/manifest.ts`, following `docs/scope.md` §1 and the 24 Oct decisions. Chatterbox is not downloaded to the phone: the fixed Swahili phrases ship as audio pre-generated with it on the VPS (C4). TranslatePsy is added by C11. The C2 spike may still change the list.

## Build for an iPhone on a Mac

The release path is EAS Build to TestFlight (card C10). For a local debug build on a physical iPhone (iOS 17+; QVAC doesn't run in the simulator):

Once per Mac: Xcode (latest, from the App Store), its command line tools (`xcode-select --install`), CocoaPods (`brew install cocoapods`), Node 24, and the Apple Developer account added in Xcode → Settings → Accounts.

```bash
git pull
cd mobile
npm ci
npx expo prebuild --clean       # writes ios/ and android/, links QVAC's addons
npx expo start --dev-client     # terminal 1: Metro, leave it running
open ios/SomaNami.xcworkspace   # terminal 2 (`npm run ios` prebuilds and opens it too)
```

Then in Xcode pick the iPhone connected by USB as the run destination and press **Cmd+R**.

- Don't use `npx expo run:ios --device`. On Xcode 27 it fails with "Can't determine id of Simulator app": Xcode 27 no longer ships Simulator.app, and `@expo/cli` 54.0.28 checks for it before every `run:ios`, even for a physical device. Building from Xcode avoids that check.
- First time: if the build stops on signing, select the **SomaNami** target → **Signing & Capabilities**, tick *Automatically manage signing* and pick the Veluvo team, then Cmd+R again. If the bundle id `com.veluvo.somanami` is taken in that team, tell Bond rather than changing it locally.
- On the phone, once: Settings → Privacy & Security → **Developer Mode** on (the phone restarts).
- The Debug build loads its JavaScript from Metro, so keep Metro running and the Mac and phone on the same network. For an offline test (airplane mode), build Release, which bundles the JavaScript into the app: **Product → Scheme → Edit Scheme → Run → Build Configuration: Release**, then Cmd+R. Set it back to Debug afterwards.
- If prebuild says QVAC prebuilds are missing for iOS, add `"installMissingPrebuilds": true` under the `@qvac/sdk/expo-plugin` options in `app.json` and say so in the PR.
- Memory: with the app running from Xcode (Product → Run on the open workspace), the Debug navigator's **Memory** gauge shows the app's footprint. iOS kills an app well before the phone's 4 GB.

No Apple certificates, profiles or keys go in this repo (`.gitignore` blocks the usual files).

## iOS: TestFlight through EAS Build

iOS tester builds are made on Expo's macOS servers with EAS Build and sent to TestFlight with EAS Submit, so no Mac is needed for a release. Config is `eas.json`:

| Profile | What it builds |
|---|---|
| `preview` | Store-signed build (not internal distribution) for a quick TestFlight check of a branch |
| `production` | Store-signed build for TestFlight and, later, the App Store |

Both use Node 24.11.0 (QVAC's bundler needs `^22.21 \|\| >=24.9`) and the newest Xcode image, and take their build number from EAS (`appVersionSource: remote`, `autoIncrement`), so every upload gets a new one. The version shown in TestFlight is `version` in `app.json`.

```bash
cd mobile
npx eas-cli build -p ios --profile production --non-interactive --no-wait
npx eas-cli submit -p ios --profile production --latest --non-interactive
```

- Credentials (distribution certificate, provisioning profile, App Store Connect API key) are set up once on Wesley's Mac with `eas credentials -p ios` and stored by Expo. Nothing Apple-related lives in this repo or on the Bond VPS; Bond only has an `EXPO_TOKEN`.
- `eas submit` needs `ascAppId` (the app's Apple ID from App Store Connect → App Information) in the `submit` profile, and `eas build` needs `extra.eas.projectId` in `app.json` (written by `eas init`).
- Expo's free plan has a small monthly allowance of iOS builds. Build only when a change needs a phone test, never upgrade or pay, and log every build in `docs/plan.md` (C10, EAS build log).
- Info.plist: camera and microphone usage strings in Swahili and English (bilingual by default, plus `locales/sw.json` and `locales/en.json`), and `ITSAppUsesNonExemptEncryption = false`, so TestFlight doesn't ask the export-compliance question on every build.
- Internal testers (users on the App Store Connect team) get a build as soon as Apple finishes processing it. External testers need Beta App Review first, which takes about a day.

## Android APK

Release APKs are built on **EAS Build** (Expo's servers, like iOS), not on a GitHub runner. `.github/workflows/android-release.yml` runs on a version tag (`v*`):

1. `eas build -p android --profile release-apk --non-interactive --wait` with the Actions secret `EXPO_TOKEN` (the job fails at once without it). The `release-apk` profile in `eas.json` makes an installable APK (`buildType: apk`, internal distribution), not an AAB.
2. It reads the APK's URL with `eas build:view --json`, downloads it as `soma-nami-<tag>.apk` and fails unless it holds arm64-v8a libraries only and has minSdk 31.
3. The `publish` job creates a GitHub Release with the APK in the public releases repo (`veluvo-softwares/soma-nami-releases`, or the repo in the `RELEASES_REPO` Actions variable), with notes from `scripts/release-notes.sh`: version, commit, what's new (the annotated tag's message, or the commit subjects since the last tag), the first-launch model download on Wi-Fi, and that it is signed with the EAS-managed key. It needs the Actions secret `RELEASES_TOKEN`, a fine-grained token with Contents read & write on the releases repo only; without it the publish step fails and the APK stays in the run's artifacts (`soma-nami-apk`). The releases repo's README is kept in `docs/releases-repo/README.md`. Tags with a suffix (`v0.2.0-rc1`) are published as pre-releases.

Every tag costs one EAS Android build from the free plan's monthly allowance. If only the publish step fails, use **Re-run failed jobs**, which reuses the APK; re-running the whole workflow starts a new EAS build.

- **arm64 only, Android 12+:** `minSdkVersion` 31 comes from `expo-build-properties` in `app.json`, and `plugins/withAndroidGradleProperties.js` sets `reactNativeArchitectures=arm64-v8a` (QVAC ships arm64 binaries only) and an 8 GB Gradle heap in `android/gradle.properties` on every prebuild.
- **Signing:** the EAS-managed Android keystore for `@mrnyamu/soma-nami`, created once and stored by Expo. Nothing signing-related lives in this repo or on the Bond VPS. Losing it would mean testers uninstall before the next APK installs, so never delete it in `eas credentials`.
- `versionCode` is kept remotely by EAS and goes up by one on every build (`appVersionSource: remote`, `autoIncrement`).

Release a tester build (the release notes are public, so write the message for testers):

```bash
git tag -a v0.1.0 -m "What testers should know about this build"
git push origin v0.1.0
```

Testers install it from the releases repo; its README has the steps.

`.github/workflows/android-apk.yml` is a manual fallback (**Actions → Android dev APK → Run workflow**): a Gradle build on a GitHub runner, debug-signed, kept as a workflow artifact. It is not on the release path and doesn't run on tags or pull requests any more; its runner shut down mid-build on PR #11.

For a local Android build: `npx expo prebuild --clean && npx expo run:android --device` (needs the Android SDK, NDK 29.0.14206865, JDK 17 and a USB-connected phone).

## Notes for contributors

- Expo SDK 54 and `@qvac/sdk` 0.22.0 are pinned on purpose (QVAC's Expo plugin is built against SDK 54). Don't upgrade during the hackathon.
- `android/` and `ios/` are generated and ignored. Configure native behaviour in `app.json`, `qvac.config.json` or config plugins.
- Run `expo prebuild` again after any `npm install`: reinstalling unlinks QVAC's native addons.
- Adding a QVAC capability means adding its plugin to `qvac.config.json` and its exact-version Android and iOS prebuild packages to `package.json` (for example `@qvac/tts-ggml-android-arm64` and `@qvac/tts-ggml-ios`); the build fails with `HOST_PREBUILDS_MISSING` otherwise.
- Nothing may start a read unless `canRead(state)` (`src/model-store/modelsState.ts`) is true. `src/AppShell.tsx` enforces it.
- Unit tests never import `@qvac/sdk` (it needs the native worker); they use `FakeModelClient` from `src/model-store/testing.ts` and `FakeReaderServices` / `FakeSpeechBackend` from `src/reader/testing.ts`.
- `api.expo.dev` is blocked from the Bond VPS sandbox, so `npx expo install` fails there; use the version listed in `node_modules/expo/bundledNativeModules.json` with npm.
